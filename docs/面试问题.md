- **参数没有通用最优值**：RRF 的 `k`、语义缓存阈值、缓存 TTL 等都应通过本项目的验证集和线上指标确定，回答时要说明实验方法与风险控制。
- **区分系统实际实现与设计方案**：如果项目没有真实统计数据，就不要把“Token 消耗下降 72%”说成已验证结果，应解释正确的统计口径。

## 一、RAG 智能客服

### 1. 父子分块原理、Query Rewrite 的适用场景

**父子分块**把文档按两个粒度组织：

- 父块保留较完整的章节或语义段落，提供上下文。
- 子块从父块中切出较短内容，用于 Embedding 和精确召回。
- 检索命中子块后，利用 `parent_id` 回取父块，再把父块作为回答上下文。

它解决的是检索粒度和生成上下文之间的矛盾：块太大，向量语义容易被稀释；块太小，命中后上下文不足。实际中需要限制回传父块的数量和总 Token 数，避免重复父块或超出模型上下文窗口。

**Query Rewrite（查询改写）**将用户原问题转换成更适合检索的表达，例如补全省略信息、展开简称、将指代词替换成实体名称，或生成关键词查询。适用于：

- 多轮对话中的“那退款呢？”需要补充上轮产品或订单信息；
- 用户用口语、简称或错别字提问，而知识库使用正式术语；
- 复杂问题需要拆成多个检索子问题；
- 原查询没有召回相关内容，触发一次受控改写重试。

不适合无条件改写简单明确的问题。改写可能改变用户原意，因此应保留原问题，限制改写次数，并可将原查询与改写查询并行召回、融合结果。

### 2. BM25 + Embedding 多路召回与 RRF

BM25 擅长关键词和精确词匹配，适合产品型号、错误码、条款号等；Embedding 擅长语义相近但用词不同的表达。通常并行召回，再做融合和去重。

**RRF（Reciprocal Rank Fusion）**常用形式：

\[ \operatorname{RRF}(d)=\sum_i \frac{w_i}{k+r_i(d)} \]

其中，\(r_i(d)\) 是文档在第 \(i\) 路结果中的名次，\(w_i\) 是该路权重，\(k\) 是平滑常数。未出现在某路结果中的文档，该路贡献为零。

实操时：

1. 先建立有人工标注相关文档的查询集。
2. 分别测 BM25、Embedding 和融合方案的 Recall@K、MRR、nDCG。
3. 先从相同权重开始，网格测试 RRF `k`、各路权重和召回数量。
4. 针对错误码、型号等精确查询，可提高 BM25 权重；自然语言、同义表达较多的问题可提高向量路权重。
5. 在离线评估通过后进行小流量线上对比，观察无结果率、点击或解决率、延迟和成本。

RRF 用排名而不是原始分数融合，避免 BM25 分数和向量相似度量纲不同。它不能自动保证结果正确，仍需要评测集和重排或阈值策略。

### 3. 语义缓存阈值如何确定，如何避免误命中

语义缓存按问题向量相似度匹配已有问答，阈值控制“多相似才复用缓存”。阈值过低会误用不相关答案；过高则命中率低。

确定方式：

- 收集真实问题，标注哪些问题可安全共享同一答案。
- 对正例、困难负例计算相似度分布。
- 选取满足误命中风险要求的阈值，再评估缓存命中率和节省量。
- 上线后分层观察误命中率、缓存命中率和用户纠正率，逐步调整。

防护方式包括：

- 对租户、用户权限、产品版本、地区、语言、知识库版本、系统提示词和模型版本做缓存隔离。
- 对订单状态、账户余额、实时库存等动态或个性化问题禁用缓存或缩短 TTL。
- 缓存答案保留来源证据 ID 和知识版本；命中时检查权限及证据是否仍有效。
- 对低置信度、涉及金额或账户操作的问题不直接复用答案，回退到正常检索和生成。
- 记录缓存命中、拒绝和用户反馈，持续审计。

**向量相似不等于答案可复用**。缓存键除了问题语义，还应包含会影响答案的上下文和权限边界。

### 4. 语义缓存过期、命中率和 Token 节省统计

缓存失效可以组合使用：

- **TTL**：短时间内有效，适合会变化的数据。
- **知识版本失效**：知识库或文档更新时，淘汰相关缓存。
- **策略/模型失效**：提示词、模型、工具或业务规则变更时更新版本键。
- **主动失效**：订单状态、价格、库存更新后清理关联缓存。
- **容量策略**：LRU/LFU 淘汰冷数据。

缓存命中率应按请求统计：

\[ 命中率=\frac{缓存命中请求数}{可参与缓存的请求总数} \]

应同时报告请求命中率和节省的 Token，不能把不允许缓存的请求纳入分母后再不作说明。

“Token 消耗下降 72%”应说明比较口径。例如同一批请求、同一模型和提示词版本下：

\[ 下降比例=\frac{基线总Token-启用缓存后的总Token}{基线总Token}\times 100\% \]

最好分别统计输入 Token、输出 Token、模型调用数和费用，并说明缓存读写本身是否计费、是否包含失败重试。若没有可复现的基线数据和样本范围，就不能把 72% 当作事实，应说“目标值”或“某次实验结果”，并给出计算窗口和样本集。

### 5. 记忆投毒（提示注入）与防护

提示注入是攻击者把恶意指令放在用户输入、检索文档、网页或长期记忆中，试图让模型忽略系统规则、泄露信息或调用不当工具。

**记忆投毒**是持久化版本：攻击内容进入对话记忆、用户画像、摘要、知识库或 Agent 状态，未来请求再次读取时继续影响模型。它既可能来自恶意用户，也可能由模型误把未经验证内容写入长期记忆。

防护思路：

- 把外部文档和记忆明确标记为不可信数据，作为引用材料而非指令执行。
- 长期记忆写入采用白名单字段、来源记录、权限检查和人工/规则审核；区分事实、用户偏好和模型推断。
- 对记忆记录租户和用户边界，防止跨用户读取。
- 工具调用使用最小权限；高风险操作由服务端校验并要求确认，不能仅凭模型决定。
- 对检索内容和模型输出进行敏感信息检查，限制密钥、个人信息等返回。
- 对写入和调用保留审计日志，支持撤销、删除和重新生成摘要。
- 使用攻击样例进行红队测试，监控工具调用越权和异常数据访问。

单靠提示词要求“忽略恶意内容”不足以构成安全边界。

### 6. 流式响应中额度耗尽、重试/切换模型和中断处理

流式响应一旦把内容发给客户端，就不能像普通请求那样透明地从头重试，否则用户会看到重复或前后矛盾的文本。

主要难点：

- 上游已生成和下游已发送的内容可能不一致。
- 断点续传通常需要模型或服务端支持续生成；仅有文本流不代表能恢复模型内部状态。
- 切换模型可能改变风格、事实和上下文，因此不能假设续写与原答案连续。
- 超时、额度耗尽、网络断开要区分可重试与不可重试错误。

常见设计：

1. **首字节前失败**：可以重试或切换模型，客户端尚未看到部分答案。
2. **首字节后失败**：默认不从头重放。可以发送明确的错误/中断事件，让客户端知道回答不完整；或者在服务端缓冲完整答案后再显示，但这牺牲实时性。
3. 若业务允许续写，可把已生成内容作为上下文请求继续生成，明确这是续写，并做长度和内容校验；它是新一次生成，不是严格恢复原采样过程。
4. 对有副作用的工具调用，使用幂等键和调用记录，不能因模型重试而重复执行。

**Token 统计**优先使用供应商最终响应里的 usage；流式接口需启用 usage 返回（如果供应商支持）。若中途断线没有 usage，可用对应模型 tokenizer 对已接收文本估算，但要标记为估算，因为分词边界、隐藏提示词、工具调用和未送达 Token 都可能造成差异。分别记录上游已生成 Token、服务端已接收 Token、下游已发送字节/文本，避免混为一谈。

对客户端可以设计事件协议，例如 `delta`、`completed`、`interrupted`，并给每段内容增加序号和 request ID。客户端去重后可恢复展示状态，但这不等于恢复模型生成状态。

## 二、多 Agent 量化投研平台

### 7. 上下文指纹、自我审批与幻觉治理

**上下文指纹**是对参与某次判断的关键输入生成稳定摘要，例如：

- 文档 ID、版本、内容哈希；
- 市场数据时间戳或数据批次 ID；
- 提示词、模型、工具和策略版本；
- Agent 输入参数及关键中间状态。

先对字段做规范化，再按稳定顺序序列化（如规范 JSON），最后计算 SHA-256。哈希不宜直接取代来源记录：它用于确认“这些输入是否变化或被替换”，同时还需要保留可追踪的原文、版本和访问路径。

**模型自我审批**是让模型自己生成决策、再由同一个模型或同一条推理链给自己打“已审核通过”的结论。这不构成独立验证。可用确定性程序校验 Schema、边界和权限；高风险建议由独立规则引擎、不同来源的数据、另一独立审核流程或人工审批。

幻觉治理可以组织为一条证据链：

1. **输入固定**：记录上下文指纹、来源版本、数据时间和模型/提示词版本。
2. **证据可追踪**：每段证据分配 `evidence_id`，保留来源、页码/位置、时间戳和哈希。
3. **结构化传递**：Agent 之间传 JSON Schema 定义的对象，不靠自由文本传递关键结论。
4. **程序校验**：检查必填字段、类型、范围、枚举、时间有效性、证据 ID 是否存在及来源是否有权限。
5. **结论绑定证据**：每个事实或建议列出支撑证据；无证据时标注推断或未知，不生成伪造引用。
6. **独立审批**：交易、仓位、资金等高风险动作由确定性风控和人工控制。
7. **审计回放**：保存输入、证据、工具结果、模型版本和输出，以便复现。

哈希只能检测输入内容是否变化，不能证明内容真实；Schema 只能保证数据结构合法，不能保证事实正确。

### 8. Human-in-the-Loop 触发、等待和会话保存

适合人工介入的场景：

- 涉及资金、下单、仓位或策略发布；
- 超出风控阈值或证据冲突；
- 数据过期、置信度不足、模型输出格式异常；
- 新供应商、新模型或高影响的业务规则变更；
- 涉及合规、隐私或权限例外。

人工等待时间长时，不能让 Agent 进程或 HTTP 请求一直占用资源。建议把流程做成可持久化的状态机：

1. Agent 将当前状态、输入、待审批动作、证据 ID、上下文指纹和版本保存到数据库/检查点存储。
2. 状态改为 `WAITING_APPROVAL`，记录审批任务 ID、创建时间、超时点。
3. 释放工作线程，通过回调或消息通知审批系统。
4. 人工决定通过、拒绝或要求补充信息。恢复时验证任务仍有效、权限未变、上下文和数据版本仍可用。
5. 恢复 Agent 执行之前，再运行一次风控和业务校验。

过期处理应显式规定：自动拒绝、转人工队列、要求重新生成，或仅允许重新确认；不能把过期的批准继续用于新版本上下文。审批日志记录审批人、意见、时间和所批准动作的指纹。

### 9. Agent Trace 与传统微服务可观测性

传统微服务 Trace 主要关注服务间调用、延迟、错误和资源使用。Agent Trace 还要解释模型的非确定性行为和决策路径：为何检索某些证据、为何调用某个工具、输入上下文是什么版本、输出如何通过校验。

核心记录：

- trace、span、session、用户请求和 Agent/子 Agent ID；
- 模型供应商、模型版本、提示词模板版本和参数；
- 输入输出 Token、延迟、费用、重试和限流信息；
- 检索查询、索引/知识版本、文档 ID、证据 ID、分数和重排结果；
- 工具名称、脱敏后的参数、执行结果、超时与幂等 ID；
- Agent 状态转换、人工审批状态、校验失败原因；
- 错误类型、重试原因和中断位置。

排错时按 Trace 找到失败 span：是检索为空、证据不相关、工具超时、Schema 验证失败，还是供应商限流。敏感提示词和原文应脱敏或按权限存储，避免 Trace 成为数据泄露渠道。Trace 本身可记录哈希和安全引用，而不一定保存完整敏感内容。

## 三、Java 后端与中间件

### 10. WebSocket Java I/O 模型与 Netty 解决的问题

面试时可这样回答：

> WebSocket 是建立在 TCP 之上的全双工通信协议。握手完成后，客户端和服务端可以在同一连接上双向发送帧。Java 中可以使用阻塞式 I/O、NIO 或异步 I/O 实现；高并发时，通常用事件驱动的非阻塞 I/O，一个或少量 I/O 线程管理多个连接，再把耗时业务任务交给业务线程池。

**Netty**是基于 Java NIO 的异步事件驱动网络框架，主要解决直接使用 NIO 时的复杂度和工程问题：

- 连接管理、事件循环和非阻塞读写；
- ByteBuf 缓冲区及编解码器；
- pipeline 式处理链；
- 背压、半包/粘包、连接生命周期、心跳和超时处理；
- 可复用的高性能网络服务器基础设施。

它不会自动解决业务幂等、消息顺序或分布式一致性，也不是 WebSocket 协议本身。Spring WebFlux、Netty 和传统 Servlet 容器的线程模型不同，回答时最好结合项目实际栈。

### 11. Kafka 在客服项目中的职责及多轮消息有序

Kafka 常用于客服系统的异步事件流，例如：

- 将客服消息送给 Agent、质检、审计、画像或统计服务；
- 让消息接收与后续处理解耦；
- 消费失败后重试或进入死信队列；
- 用日志方式保留事件，支持一定范围内的回放。

要保证同一会话内有序，通常把 `conversation_id` 作为 Kafka key，使同一会话消息进入同一个分区。Kafka 只保证**分区内**有序，不保证不同分区间有序。

还需要保证生产端顺序：对同一个会话避免多个并发生产者乱序发送；必要时启用幂等生产者和合适的事务设置，并在事件里带 `conversation_id`、`sequence` 或业务版本。消费者对同一分区内的记录按顺序处理；如果采用异步并发处理，要在会话级串行化或基于序号重排。

### 12. Kafka 积压处置与分区、消费者关系

先观察积压量、积压增长速度、最老消息年龄、消费速率、处理失败率和下游依赖。不要只看总 Lag。

处理步骤：

1. 判断是生产突增，还是消费者变慢/卡死。
2. 看消费者错误、重试、外部接口延迟、GC、数据库连接池和分区是否倾斜。
3. 临时扩容消费者、优化批处理或处理逻辑，必要时对低优先级流量限速。
4. 对毒消息设有上限的重试和死信队列，避免无限重试阻塞分区。
5. 评估是否需要增加分区；增加分区会改变 key 的映射，可能影响会话有序性与消费并行策略。
6. 恢复后验证端到端业务完整性，不只看 Lag 降到零。

同一个消费组里，**有效并行消费数最多等于分区数**；消费者数超过分区数时，多出的消费者空闲。消费者少于分区数时，一个消费者可负责多个分区。分区增加不是唯一扩容办法：如果瓶颈在数据库、外部 API 或单条消息耗时，盲目增加消费者可能加重下游压力。

### 13. MySQL 写工单与 Kafka 发消息的一致性、幂等

直接先写 MySQL 再发 Kafka，可能出现“数据库成功、消息失败”；先发 Kafka 再写数据库，则可能“消息成功、数据库失败”。两个独立系统通常没有一个共同的本地事务，因此不能简单宣称两边原子提交。

常用方案是 **Transactional Outbox（本地消息表）**：

1. 在一个 MySQL 事务内写工单，同时写一条待发送的 outbox 记录。
2. 后台发布器扫描待发送记录，发送到 Kafka。
3. 收到 Broker ACK 后标记为已发送；发送失败则按退避策略重试。
4. 可能重复发布，因此消费者必须幂等处理。
5. 监控 outbox 积压、发送失败和最老记录年龄，并提供人工补偿能力。

幂等可以使用稳定业务事件 ID，例如 `ticket_id + event_version`，并让消费者在业务事务内执行去重：

- 建立消费记录表或唯一约束；
- 在同一数据库事务中登记事件 ID 并更新业务数据；
- 已处理过的事件直接确认，不重复执行副作用；
- 如果副作用涉及其他系统，也要传递幂等键或采用对应的 outbox/补偿流程。

**ACK 不能单独保证端到端恰好一次**：Producer 收到 ACK 代表 broker 接收了消息，但确认过程可能丢失，导致重发；消费者完成数据库更新后、提交 offset 前崩溃，也会再次消费。可靠设计通常允许至少一次投递，并通过去重实现业务上的幂等效果。
